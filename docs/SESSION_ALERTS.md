# Session alerts MVP

Implemented in `feat/session-alerts`, based on `849245c`. This is a development change, not audit evidence or real-provider acceptance. No real provider, user profile, system settings, push, or staging worktree was used.

## Behavior

- The header **Avisos** button is global, including when the sidebar is hidden or a task is open. It opens the session list with the alert filter and clears search. A row opens its session. The banner only offers navigation and marking seen; permissions still require the existing contextual native confirmation.
- Claude/Codex PTY sessions report **La sesión emitió una alerta** and **El proceso terminó**. Raw output never counts as attention: spinner, progress and cursor redraws must not generate banners, unread counts, Dock badges or native notices. No terminal-text heuristics are used. BEL and OSC 9 notifications / OSC 777 `notify;` use the installed xterm public parser. OSC 9 numeric subprotocols (including progress) are ignored. Replay cannot emit activity alerts. Live-to-exited/stopped/failed process transitions are deduplicated independently of status/event delivery order.
- Explicit protocol signals are collected when the session is not the focused session in a visible, focused app window. Viewing consumes activity. An observed process end can remain until viewed even if the selected session has ended.
- Lifecycle incidents retain existing attention-filter coverage: failed, interrupted, unknown and `needs_attention`. The latter means custody/recovery uncertainty, never a permission wait. A confirmed runner lifecycle change clears or replaces that cause; marking seen does not release custody, stop a process, or resolve it.
- Relevant structured app-server sessions are queried independently of pane visibility, filters and task screen. Two workers maximum, one collection at a time, every three seconds. Finished history without known pending permissions is skipped. Collection is detached from terminal/status polling; completion refreshes the UI. Reconnect/version and session-generation guards discard obsolete reads.
- `pendingRequestCount` handles bounded/truncated summaries. Request identity includes generation and request ID. Read errors retain last known data as **sin confirmar**. Prior-generation requests are **caducado**, not resolved. Stale/expired observations do not add to the confirmed header number (`+ ?` indicates uncertainty), and never generate native notices.
- Initial lifecycle and first successful permission snapshots per generation are quiet: listed, without a new-alert banner or native notice. Later changes are unseen. Seen permission/custody causes remain listed until the source changes. Repeated unchanged snapshots do not re-alert. Seen state and activity are window-local; they are not persisted across app launches. *(Historical: MVP behavior. Since 1.4 E the runner keeps declared state and seen sequences; see [Estado y vistos en el runner (1.4 E)](#estado-y-vistos-en-el-runner-14-e).)*

## Native notifications

Actual `tauri-plugin-notification` 2.8.1, pinned for Rust and JavaScript. The local `main` window has only `allow-is-permission-granted`, `allow-request-permission`, and `allow-notify`; no remote origins or broad default notification capability. The Rust builder initializes the plugin; the frontend calls its official API, not an unconfigured WebKit Notification implementation.

**Información → Activar avisos de macOS…** opts in for this app opening. Default off on every launch. Only this click can call the permission request API. No startup/background permission requests or OS settings changes. Existing alerts at activation are excluded. New unseen, non-stale background alerts are grouped over 1.5 seconds and deduplicated. Acknowledgement, focus, disconnect, disabling, or window disposal can suppress a queued notice. The notice has fixed generic copy: no session titles, paths, terminal content, request details, or session deep link.

Delivery is best effort, only while Jauría is open. No sound, critical alert, scheduled delivery or click-to-session action is implemented. Importantly, the plugin's desktop `permission_state` / `request_permission` implementation always returns `Granted`; it does not prove macOS notification settings or delivery. `sendNotification` returns void, with no delivery receipt. The settings copy states these limits. No actual OS notification or permission prompt was exercised for this change.

Primary references: [Tauri notification setup and permissions](https://v2.tauri.app/plugin/notification/), [official JavaScript notification API](https://v2.tauri.app/reference/javascript/notification/). The pinned plugin's `src/desktop.rs` documents unconditional desktop permission reporting; its `dist-js/index.js` exposes the notification API through the plugin-installed implementation.

## Terminal geometry regression

Until delivery 1.4 A, notification and connection messages shared an always-present 50 px rail. Since 1.4 B there is no rail: see «Avisos sin barra fija (1.4 B)» below. Showing, consuming, dismissing or replacing a message still does not change terminal rows or columns. This matters for native Codex: changing the PTY geometry sends SIGWINCH, causing a redraw that can jump away from the reading position. The native focus regression was reproduced with the old layout (31 → 34 rows) and checked after the fix (121 × 31 throughout; zero resize events; same runner and PTY process).

`node --test tests/browser/notification-geometry.test.ts` checks host bounds, real xterm dimensions, every rendered frame and native resize-request counts in Chrome/WebKit at 1220 × 800 and 760 × 640. The old source at `5431021` failed all four cases of the original version; the 1.4 B rewrite is described below. The browser suite runs files serially: simultaneous browser-heavy fixtures made the older detached-viewport baseline timing-dependent. This test evidence is separate from security-audit reproductions.

## Activity is not an unread alert

Raw PTY output, including progress redraws, never enters the attention ledger. The legacy output signal is explicitly ignored at the model boundary as well as omitted from the renderer callback. BEL, supported OSC notifications, process termination, observed lifecycle incidents and structured pending permissions keep their existing semantics. The global header distinguishes new alerts from already-seen pending causes; seeing a pending permission does not approve or resolve it.

## Actividad y avisos desde 1.3.1

Esta sección describe el comportamiento actual. Los apartados anteriores documentan el MVP histórico y sus cifras de prueba, no la nueva versión.

- **Actividad** siempre está disponible en la barra lateral. Ordena las sesiones observadas por acción requerida, avisos explícitos, turnos o procesos terminados, trabajo declarado, espera y progreso no informado. Desde la entrega 1.4 A es la agrupación **Por estado** de la sección Agentes (dentro de **Abiertas**); **Por proyecto** es la predeterminada y ordena cada grupo con la misma prioridad. Solo un reporte `working` muestra el anillo giratorio.
- `running` describe un proceso abierto, no trabajo activo. Solo OSC 7501 raíz `working` se muestra como **Trabajando**, con tiempo observado en esta ventana *(histórico: con un runner que anuncia `agentAttentionVersion` el tiempo sale de `turnStartedAt` del runner; ver 1.4 E)*. Sin reporte, la sesión queda **Abierta · progreso no informado**. Los reportes de hijos, preguntas y campos de texto siguen ignorados; no se inspecciona salida cruda ni se infiere un porcentaje.
- `blocked/error` constituye una causa persistente mientras el programa lo declara. `working → done/idle` produce un fin no visto que persiste si después llega `idle`; abrir la sesión lo marca visto. Un reporte nuevo de `working` borra ese fin pendiente. Ver la sesión no responde permisos ni repara un fallo. El estado reportado y el visto se pierden al reconectar o cerrar la interfaz *(histórico: desde 1.4 E el runner conserva ambos; esta frase describe la interfaz sin esa capacidad)*.
- Desde 1.4 B no hay barra de avisos: la causa prioritaria aparece en la etiqueta de estado de la cabecera del panel, en la campana de la barra superior (con su lista emergente) y en la barra de estado. **Abrir sesión** y **Marcar vistos** están en esa lista; ninguna de las tres superficies cambia la altura del terminal. **Marcar vistos** afecta solo a la presentación; las causas persistentes permanecen hasta que su fuente cambia. La notificación nativa opcional usa una de tres categorías genéricas: atención, actividad finalizada o aviso. Nunca contiene títulos, rutas, salida ni detalles de permisos. Su entrega sigue sin recibo y el clic en macOS no abre automáticamente la sesión.
- La implementación está en `program-status.ts`, `attention.ts`, `session-activity.ts` y `main.ts`. La revisión con Claude y el contraste con Herdr están en [HERDR_REVIEW.md](HERDR_REVIEW.md#actividad-y-avisos-en-131). Las pruebas usan sesiones sintéticas y el xterm real en Chromium/WebKit; no prueban notificaciones del sistema ni proveedores reales.

## Avisos sin barra fija (1.4 B)

La barra de avisos de 50 px se retiró del flujo. El aviso prioritario se muestra en tres sitios de alto fijo y en una lista flotante:

- **Cabecera del panel (32 px).** La etiqueta de estado (indicador y texto, con tinte naranja cuando la sesión te necesita) cambia de contenido, nunca de alto: la cabecera es `nowrap`, recorta y tiene alto mínimo y máximo de 32 px.
- **Campana de la barra superior (42 px).** Muestra el número de avisos nuevos y abre una lista flotante (`#attention-banner`, posición absoluta) con cada sesión, su motivo, «Sin ver»/«Visto» y **Abrir**, más **Ver en la lista** (el filtro de la barra lateral), **Marcar vistos** y **Abrir sesión** (la sesión prioritaria). Escape (desde la lista o desde la propia campana desplegada) o un clic fuera la cierran y el foco vuelve a la campana.
- **Barra de estado (28 px).** «N te necesita(n)» (botón: abre la sesión prioritaria), «N terminó/terminaron» y «N trabajando». «Sin avisos» solo aparece cuando la campana está a cero; un aviso que no cuenta ningún contador se muestra como «N avisos».
- Una región `aria-live="polite"` visualmente oculta anuncia los avisos nuevos sin ver; no repite los que siguen igual.

Los avisos genéricos y los errores de conexión son una notificación flotante en la esquina inferior derecha (máximo 96 px con desplazamiento propio). El selector de sesión y el menú «…» del panel también flotan. Ninguno ocupa espacio del terminal. *(Hasta 1.4 D también flotaba el contexto de relevo, retirado con las tareas Git.)*

`tests/browser/notification-geometry.test.ts` se reescribió para este diseño sin relajar lo que protege: en Chrome y WebKit, a 1220 × 800 y 760 × 640, comprueba el rectángulo de `.terminal-host` en cada fotograma, las columnas y filas reales de xterm y que no haya RPC `resize` adicionales al llegar un aviso explícito (BEL, OSC 9, OSC 777), al consumirlo, al marcarlo visto, con avisos y errores largos a la vez, durante la recuperación del historial, al abrir y cerrar la lista de avisos (clic y Escape), con los estados de programa `working`, `blocked`, `done`, `idle` y `clear` en la cabecera del panel, con el contador de la barra de estado y al abrir, filtrar y cerrar el selector de sesión. También comprueba los altos fijos de la barra superior, la cabecera del panel y la barra de estado, y que las teclas escritas en el buscador del selector no llegan al PTY. Una mutación de control (la notificación con `position: static`) hace fallar los seis casos originales. ## Estado y vistos en el runner (1.4 E)

Desde 1.4 E el runner, no la ventana, observa las señales explícitas del PTY y guarda el estado declarado y lo visto. La interfaz deja de ser la fuente de verdad cuando el runner anuncia el contrato (`agentAttentionVersion: 1` en `status`); frente a un runner anterior sigue el comportamiento de las secciones anteriores. Cómo lo usa la interfaz está en [La interfaz con el runner (1.4 E)](#la-interfaz-con-el-runner-14-e). El contrato exacto está en [DEVELOPMENT.md](DEVELOPMENT.md#atención-de-agentes-en-el-runner-14-e).

**Qué observa.** `agent_signals.rs` lee cada byte de salida de cada sesión PTY una sola vez, aunque la secuencia llegue partida entre lecturas, y lo interpreta como xterm 5.5: primero decodifica UTF-8 con las reglas de su decodificador (descarta secuencias inválidas, sobrelargas, sustitutos y U+FEFF) y después aplica su tabla de transiciones. Reconoce OSC 7501 raíz (`working`, `blocked`, `error`, `done`, `idle`, `clear`) con las reglas y el presupuesto de 1 KiB de `parseProgramStatus`, BEL ejecutado (también dentro de ESC y CSI) y notificaciones OSC 9 y OSC 777 `notify;` con las reglas de `terminal-attention.ts`. OSC 9 y 777 se deciden por sus primeros caracteres y no se guardan, así que una notificación larga avisa igual que en el cliente; solo el límite de xterm (10.000.000 unidades UTF-16 de payload) la descarta. Los C1 codificados en UTF-8 (`C2 9D` = U+009D OSC, `C2 9C` = ST, U+0090/U+0098/U+009E/U+009F/U+009B) actúan como en xterm; un byte 0x9D suelto no. Un carácter ≥ U+00A0 termina las cabeceras ESC/CSI/DCS y SOS/PM/APC, como el error de xterm. Ignora la salida cruda y los subprotocolos numéricos de OSC 9 (progreso `9;4`). Los vectores compartidos están en `desktop/tests/fixtures/program-status-vectors.json`. Diferencia que queda: los dígitos del identificador OSC no tienen límite propio (xterm tampoco limita el identificador, pero lo acumula como número de coma flotante); no cambia ningún resultado. El modo estructurado de Codex no usa OSC: no tiene estado y nunca se muestra como trabajando.

**Declaración del PTY.** El estado es lo que declara la salida del terminal, no la verdad del agente. Cualquier programa de la sesión, o un `cat` de un archivo que contenga una secuencia válida, puede declararlo. El runner nunca publica el contenido de la secuencia (título, mensaje o texto de 9/777): solo un enumerado y el índice del frame que la completó. Solo el payload de OSC 7501 pasa por un búfer fijo de 1 KiB, que se pone a cero al terminar o descartar la secuencia.

**Avisos y visto.** Cada aviso toma el siguiente `alertSeq` de su sesión y queda registrado por tipo: `needs` (entrar en `blocked`/`error`), `finished` (`working`/`blocked`/`error` → `done`/`idle`), `bell`, `notify` (como mucho uno por tipo, sesión y segundo), `ended` (fin de proceso confirmado: `exited`, `stopped` o `failed`; `needs_attention` sigue siendo una causa del estado de la sesión, no un `ended`) y `permission` (solo una solicitud de Codex nueva confirmada en el registro, con su `requestId` y generación). Un aviso está pendiente mientras su secuencia supera `seenSeq`. `mark_seen` solo sube `seenSeq` hasta `min(through, alertSeq)` y solo para la encarnación actual del registro (`epoch`): marcar lo que se pintó nunca oculta un aviso que llegó después, dos clientes que marcan en cualquier orden quedan en el máximo, y un cursor de una fila podada y creada de nuevo se rechaza sin efecto. Marcar visto no responde un permiso ni libera custodia.

**Sustitución.** `needs` dura mientras el programa declara `blocked`/`error`, como en el tracker del cliente (`ProgramStatusTracker`): cualquier declaración posterior que salga de esos estados lo retira, también dentro del mismo `printf` (`blocked` → `working`). Por diseño: si el agente se desbloqueó solo, ya no necesita a la persona. `finished` **no** se retira por una transición posterior (diferencia deliberada con el tracker del cliente, que lo borra al volver a `working`): un fin de turno sin ver queda pendiente hasta `mark_seen`, aunque el agente ya haya empezado otro turno o declare `clear`, porque con agentes dirigidos por otros agentes la persona necesita saber qué terminó mientras no miraba. Si llega otro fin de turno, el mismo aviso pendiente pasa a la secuencia nueva. El fin del proceso y el reinicio del runner nunca retiran un aviso sin ver. Tras el fin del proceso la sesión queda sellada: los bytes que el lector aún drene no cambian estado, turnos ni avisos (tampoco BEL ni notificaciones: la sesión terminó).

**Turnos.** Un turno empieza al declarar `working` sin turno abierto, continúa durante `blocked`/`error` y termina en `done`, `idle` o `clear`. `lastTurnMs` se mide con reloj monotónico. Si el proceso termina con un turno abierto, se cierra con `turnInterrupted` y su duración real; si el runner se reinicia, los turnos abiertos pasan a interrumpidos sin duración.

**Durabilidad.** La tabla `agent_attention` de `runner.sqlite` la escribe solo el hilo `agent-attention` con su conexión; el lector del PTY nunca toma la base principal. `mark_seen` responde cuando su cambio está confirmado (`durable: true`) o, si SQLite sigue ocupado tras 2 s, con `durable: false` y el visto solo en memoria; solo una llamada espera a la vez y las concurrentes responden de inmediato (posiblemente `durable: false`), de modo que `mark_seen` nunca agota los cupos del socket que necesitan `status`, `input` o `stop`. Los demás cambios se confirman en lotes en menos de 250 ms más el tiempo de SQLite; una caída dentro de esa ventana pierde como mucho esos cambios, nunca un visto confirmado. El cierre ordenado espera (acotado) a que los hilos de espera de los PTY y los workers de Codex terminen y después vacía la cola con el mejor esfuerzo durante como mucho 3 s: si SQLite sigue ocupado ese tiempo, lo pendiente se pierde. Si la tabla existe con otra definición, el runner sigue solo en memoria y no rechaza el perfil.

**Retención.** Eliminar o compactar el historial de una sesión no borra su atención: un aviso sin ver sobrevive a purgar la salida. Al abrir, el runner borra las filas cuya sesión ya no existe. Las filas de sesiones cuyo proceso terminó de forma confirmada y con todo visto se limitan a 512, empezando por las más antiguas: al abrir y también en ejecución, cuando pasan de 576. Nunca se descartan filas con avisos pendientes, de sesiones vivas ni con un fin incierto; las de Codex estructurado solo se podan al abrir. `status` envía `agent` solo para sesiones vivas o con avisos pendientes, como mucho 128 (primero las pendientes), e indica `hasMore` y los totales exactos; `terminal_live` siempre trae el `agent` de su sesión.

**Compatibilidad.** Con la app 1.3.x el runner solo añade claves a `status` y `terminal_live`; los frames no cambian y su lector en xterm sigue igual. Los avisos que nadie marca se acumulan y aparecen como pendientes cuando se vuelve a la app 1.4. Un runner 1.3.x abre el perfil y no toca la tabla (comprobado con el binario de v1.3.3).

## La interfaz con el runner (1.4 E)

La interfaz elige la fuente de atención al conectar, según `status`. Las dos implementaciones están en `desktop/src/attention-source.ts`, tras una interfaz común; `main.ts` solo pide a la fuente actual la lista de avisos, la actividad de cada sesión, la palabra de estado y la duración. Barra lateral, pestañas, cabecera del panel, barra de estado, campana y su lista, pies de tarjeta de Pulso, paleta y Dock leen esa misma respuesta, así que siempre coinciden.

**Modo runner** (`agentAttentionVersion: 1`). El `agent` de cada sesión, de `status` o de `terminal_live`, es la única fuente del estado declarado, de la duración del turno y de los avisos pendientes. El lector de OSC del xterm sigue registrado, pero no genera estado ni avisos: con los dos activos los avisos se duplicarían.

- **Estado.** «Trabajando» solo con `state == "working"`; un turno abierto sin ese estado, o Codex estructurado (sin `state`), es «progreso no informado». La duración sale de `turnStartedAt` mientras trabaja y de `changedAt` en los demás estados; en espera, el detalle indica la duración del último turno (`lastTurnMs`) o que se interrumpió. Como viene del runner, sobrevive a cerrar la ventana, reconectar y recargar.
- **Avisos.** `needs` (el agente pide atención o informa un error) dura mientras se declara; si ya se vio, la sesión sigue en «Necesitan tu acción» sin contar como nueva. `finished` («Turno terminado») sigue pendiente aunque el agente vuelva a trabajar: la fila muestra la marca de terminado con «Trabaja de nuevo · desde hace…» y la cabecera del panel dice «Trabajando». `bell`/`notify` son «Aviso del terminal»; `ended`, «Proceso terminó». `permission` significa que llegó una solicitud y nadie la vio, no que siga sin responder: el permiso pendiente, su recuento y la distinción caducado/sin confirmar siguen saliendo de `codex_state`. Si `codex_state` no muestra ninguno, la sesión aparece como «Solicitud de permiso sin ver». Las causas del ciclo de vida (`failed`, `interrupted`, `needs_attention`) siguen siendo locales, como antes.
- **Lista incompleta.** Con `agentAttention.hasMore`, la campana y el Dock suman las sesiones pendientes que `status` no listó (`pendingSessions` menos las listadas) y la lista de la campana termina con «y N más sin listar»; nunca se presenta como completa. El runner lista primero las sesiones con avisos pendientes, después las vivas, de la más reciente a la más antigua, como mucho 128.
- **Cada `status` es la verdad.** Un registro que el `status` actual no lista se descarta en ese ciclo: si había `hasMore` pasa a contarse dentro de los ocultos; si no, ya no tiene nada pendiente. Así, una sesión vista en otra ventana o cuyo `needs` se resolvió deja de aparecer como pendiente aunque el runner siga recortando la lista. La única excepción es la sesión cuyo `terminal_live` llegó después del `status` anterior (está a la vista: `terminal_live` siempre trae su `agent`). Del registro descartado solo se conserva su `alertSeq` como línea base de macOS, para no anunciarlo otra vez si reaparece, y las marcas de visto en vuelo; la respuesta de `mark_seen` no lo vuelve a crear.

**Qué cuenta como «ver».** El visto vuelve al runner con `mark_seen`, siempre con el `epoch` y el `alertSeq` del mismo objeto `agent` que se pintó en el último render (`RunnerAttentionSource.paint` guarda esa instantánea; un `agent` posterior nunca se usa para marcar).

- **Automático:** solo para avisos con `frame`, cuando la sesión se está atendiendo: documento visible, ventana enfocada, vista de terminal (no Pulso), nada que cubra el terminal (ningún `<dialog>` abierto —paleta, Configuración, nueva sesión, cambiar nombre, terminar, cajón de Pulso— ni el cajón lateral con su velo en ventanas de 860 px o menos) y sesión del panel enfocado, xterm ya consumió ese frame (el cursor del stream, que avanza tras el callback de escritura, es ≥ `frame` en la generación actual del runner), la vista salió del replay (`liveReady`) y hay conexión. Si un aviso aún no se consumió, `through` se queda justo por debajo de su secuencia.
- **Explícito:** seleccionar o abrir la sesión (barra lateral, pestaña, lista de avisos, paleta, «N te necesita») y **Marcar vistos** marcan todo lo pintado, también los avisos con `frame: null` (otra generación, `ended`, `permission`), que nunca se marcan solos. Si la vista está en replay, la marca espera y se envía al terminar.
- Nunca durante el replay del historial o del stream, sin conexión ni antes de `liveReady`. Un cambio de `status.generation` descarta las marcas pendientes. Un fin de proceso mientras miras la sesión (sin `frame`) queda pendiente hasta que la vuelvas a abrir o pulses Marcar vistos.
- Las marcas se agrupan (como mucho 64 por llamada, una llamada a la vez) y solo se llama cuando hay una secuencia nueva que marcar. La interfaz muestra el visto en el acto; si la llamada falla, lo conserva y reintenta a los 2 s. `rejected: "epoch"` sustituye el registro por el devuelto y no reintenta con el `through` viejo. `durable: false` no es un error visible: el visto vale ya y podría reaparecer tras una caída del runner.

**Primer contacto.** Con el runner, la regla de «primera instantánea silenciosa» deja de aplicarse a sus avisos: los pendientes cuentan en la campana, la barra de estado y el Dock desde el primer render. Las notificaciones de macOS toman como línea base el `alertSeq` de cada sesión en el primer `status` de cada conexión o generación, antes del primer render, y solo avisan de secuencias posteriores; al reconectar con las notificaciones ya activadas no se repiten. Si ese primer `status` traía `hasMore`, una sesión que ya estaba en su lista de sesiones pero sin `agent` (recortada) toma su línea base al verla por primera vez, sin avisar de lo anterior; una sesión cuyo id aparece por primera vez después nació tras conectar y no tiene línea base: sus avisos sí generan notificación. Categorías: `needs` y `permission` → «Necesita tu atención»; `finished` y `ended` → «Actividad finalizada»; `bell` y `notify` → «Aviso de sesión». El texto sigue siendo genérico. Las causas del ciclo de vida conservan su primera instantánea silenciosa.

**Regla de «atendida».** Es una sola (`isAttended` en `main.ts`) para los dos modos: decide el visto automático del runner, si el lector de xterm del modo degradado cuenta un BEL como aviso o lo da por visto, si una notificación de macOS es elegible y si se consume la actividad. Un terminal tapado por el cajón lateral en ventana estrecha no se está atendiendo.

**Modo degradado** (runner 1.3.x, sin la capacidad): todo como en las secciones anteriores, con esa regla de «atendida». Lector de OSC en xterm, `ProgramStatusTracker`, visto solo en la ventana, primera instantánea silenciosa y la relectura de Pulso al terminar un turno.

**Geometría.** Ningún cambio de estado, aviso o visto que llegue por `status` o `terminal_live` cambia el tamaño del terminal ni envía `resize`.

**Pruebas.** `tests/attention-source.test.ts` (mapeo de `agent`, reglas de marcar visto, un `agent` más nuevo entre pintar y marcar, línea base de macOS con sesiones existentes y nuevas, `hasMore` y descarte de registros omitidos); `tests/native-attention.test.ts` (categoría de las claves del runner y texto fijo); `tests/program-status-vectors.test.ts` recorre los vectores compartidos con `parseProgramStatus` y con el xterm instalado (entero, cada corte en dos y byte a byte); `tests/browser/program-status-parity.test.ts` repite la paridad en Chromium y WebKit, y `tests/browser/agent-attention.test.ts` cubre los dos modos en la app real con una frontera Tauri sintética cuyo `status` se construye como `status_into` (tope real de 128, omisión del resto): una sesión vista en otra ventana deja de estar pendiente con la lista recortada, y el cajón lateral a 760 px, la paleta y Pulso impiden el visto automático.
